# kyuura-engine-gui

[kyuura-engine](https://github.com/moheronemy/kyuura-engine) の公開クライアント API（`kyuura_engine.client_api`、契約 `kyuura-client-api`・形式 1）を使う、**ローカル確認用の最初の GUI** です。

> **ローカル専用です。** 一台の端末でプレイヤー0・プレイヤー1・観戦者の表示を切り替えて確かめるためのもので、認証済みのオンライン対戦・公開サーバーではありません。画面の切り替えと、接続層が渡す入口の識別子は、本人確認・強固な認証ではありません。この切り替えの仕組みを、将来の公開サーバーの権限制御に流用しないでください。

エンジンの処理は GUI へ移植していません。ゲーム規則・合法性の判定・カード効果は、すべてエンジンの `ClientHub` が行います。

## 構成

```
web/       フロントエンド（Vite・React・TypeScript）。/api を Vite のプロキシで接続層へ送る
  src/api/       契約の値（contract.ts）・JSON の型（types.ts）・実行時検証（validate.ts）・通信層（transport.ts）
  src/state/     入口ごとの画面の状態（取っ手・取り直し・遅れた応答の破棄）・送信の門・ログの要約
  src/components 盤面・状態・候補・coverage・決定の入力・診断・ログ・作成の画面
  src/cards/     カード画像（公開カード定義の検証・kyuura-card-renderer の入口・描画の部品）
  e2e/           実エンジンへのブラウザの接続確認（Playwright）
server/    ローカル接続層（Python・FastAPI）。ClientHub を包む薄い層。127.0.0.1 だけで待ち受ける
  kyuura_gui_server/  app.py（HTTP の口）・local_match.py（入口の保持・直列化・更新の保持）・decks.py・scenarios.py・safety.py・card_definitions.py（描画用の公開カード定義）
  tests/              接続層のテスト（実際の固定版エンジンへつなぐ）
  tools/              検証用の固定例の作り直し
contract/  GUI が前提にする契約の値の表（TypeScript と Python のテストが同じ表を読む）
scripts/   setup・dev・test の補助（Node）
```

ブラウザは Python を import しません。ブラウザ →（Vite のプロキシ）→ 接続層（HTTP の要求・応答）→ 入口の `handle(dict)` → エンジン、の順です。WebSocket は使いません。

## 必要なもの

- Node.js 20 以上（確認: 24.18.0・npm 11.16.0）
- Python 3.11 以上（確認: 3.14.6）
- git（エンジンを固定コミットから取得する）
- 接続確認（`npm run e2e`）だけ: Microsoft Edge（既定）。ほかのブラウザは `KYUURA_E2E_CHANNEL=chrome` など

## 番の基本の操作（U7-3）

エンジン 0.165.0（U7-3）で加わった 4 種類を、エンジンの候補（`candidates`）→ 入力の制約（`inputs`）→ 検査（`check`）→ 送信（`submit`）だけで扱います。候補は公開の `kind` で表示を決めます（`c1` などの番号や並びの先頭には依存しない）。GUI はベンチの空き・つけられる先・進化の元・にげるの費用を推測しません。

| 操作 | 段（送る順） | 画面 |
|---|---|---|
| たねポケモンをベンチに出す（`play_basic`） | 1. 手札のカード | 候補の選べるものだけ。`bench` の数と上限は表示だけ |
| エネルギーをつける（`attach_energy`） | 1. 手札のエネルギーカード → 2. 自分の場のポケモン | 2 段目は 1 段目で選んだ番号の `options_by_choice` の組だけ。送る前に check が必須（GUI の決まり。下の「送る前の check」） |
| 進化させる（`evolve`） | 1. 手札の進化カード → 2. 自分の場のポケモン | 同上。本人のうらのポケモンは裏面（カード ID なし・`unverified`） |
| にげる（`retreat`） | 1. 入れ替えるベンチのポケモン → 2. トラッシュするエネルギー（0 枚以上・選んだ順） | 枚数（`count`）と個数（`units` の合計・`total_units`）を分けて表示。本人のうらのバトル場のポケモン（P6・v0.174）は `cost_evaluation` で費用・個数を「評価していない」と表示（下の「本人のうらのバトル場のポケモンのにげる」）。送る前に check が必須 |

- **送る前の check（GUI の決まり）**: エネルギーをつける（`attach_energy`）は、1 枚（2 段）・2 枚（カツラの 3 段目 `energy2`）とも、今の取っ手・今の候補・今の入力への check が通っている場合だけ送信できます（`contract/kyuura-client-api-v1.json` の `check_before_submit_kinds`）。これは GUI が要求する条件で、エンジンが要求する条件ではありません（エンジンは check なしの submit も受け付け、送信の応答で受理・拒否を決めます）。送信のボタンの無効化と、送信の処理の入口（`web/src/state/checkGate.ts` を `useEndpointSession` の submit が呼ぶ）の両方で同じ条件を確かめ、満たさなければ submit の要求を出しません。1 段目・2 段目・3 段目（2 枚目を選ぶ・変える・外す）を変える、候補・取っ手が変わる、閲覧者を切り替えると、前の check の答えは使いません。元の入力に戻しても、変える前に始めた check の遅れた答えは使わず、検査し直します。check と submit を自動で実行・再送しません。check が通っても受理・完走の保証ではありません。にげる（`retreat`）も、v0.174 から種類として `check_before_submit_kinds` に入れ、おもて・本人のうらのバトル場のポケモンとも送る前に check が必須です（以前は `total_units` のある段があるときだけ求めていた。P6 の段には `total_units` がないので、段の項目では決めない）
- **2 段の入力**（`depends_on_stage`・`options_by_choice`）: 1 段目を選ぶまで 2 段目は選べない。2 段目は組ごとの `eligible`・`processability`・`reasons` で表示する（同じポケモンでも、1 段目のカードによって区分が違うことがある）。1 段目を変えたら 2 段目の選択を捨てる
- **にげるの費用**: 必要な個数（`total_units`）と、選んでいるカードの個数の合計・枚数を表示する。1 枚で 2 個を出すカード（`units: 2`）・特殊エネルギー（`special`）・0 個（エネルギーを選ばずに送る）・こんらん（`confused`。受理のあとにコイン）を扱う。個数が範囲内でも合法とは表示しない（余る個数・読み方で変わる数などの未裁定はエンジンの検査が決め、GUI は決めない）。**今の入力への check が通るまで送信できない**。トラッシュの並びは選んだ順のまま送る
- **check の扱い**: check の答えは、どの入力への答えかを持つ。表示・送信の条件に使うのは、今の取っ手（選び直すと作り直す）・今の入力と同じ入力への答えだけ。入力を変えたら前の答えは使わない。遅れて届いた答えも、今の入力と違えば使わない。check が通っても受理・完走の保証ではなく、結果は submit の応答で決まる
- 受理のあとは選択と古い候補を捨てて取り直す。`refetch_required`（check・inputs・submit）でも取り直す。二重クリック・並行送信は送信の門で止め、submit は自動で再送しない。「やめる」は選択を捨てるだけで何も送らない
- **coverage**（U7-3 からの意味）: `scope_kinds` は「評価した種類（番を終える・基本の 4 種類。U7-4 でワザ、U7-5 で 5 種類も）」と「未対応の種類（`not_covered_kinds`。U7-4 で 7 種類、U7-5d で 2 種類、U7-5e で `check_face_up_deck` の 1 種類、v0.172 の番のプレイヤーの MAIN では空）」。`offered_kinds` は候補に出した種類だけで、評価して出さなかった種類（この状態ではゲーム上できない）は「評価して候補に出さなかった種類」と分けて表示する。番の候補は `partial`
- **処理可能性**: `supported` は候補の `guarantees` にある範囲の保証（受理のあとの全分岐の完走ではない）、`may_stop_later` は受理のあとに止まりうる（`reactions_not_evaluated`）、`unverified` は保証なし（最終の判定はエンジン）、`unresolved_ruling`・`not_implemented`・`technical_limit` は送れない（ゲーム上の禁止とは表示しない）。入力の公開区分（`input_disclosure`）は別の軸として表示する
- **知らない入力**: 入力の段に契約の表（`contract/kyuura-client-api-v1.json` の `stage_keys`）にない項目があれば「不明な応答」として操作を止める。GUI が入力の画面を持たない種類（`gui_operable_kinds` にない種類）の候補は表示だけで選べない。v0.172 の表示だけの種類（`display_only_kinds`。`check_face_up_deck`）は位置を表示するだけで、check・submit を呼ばない

## ワザの宣言（U7-4）

エンジン 0.166.0（U7-4）のワザの宣言（`use_attack`）を、候補 → 入力 → check → submit だけで扱います。入力の画面は段の `role`（`attack` → `declaration_options`）・`addon`・`options_by_choice` から組み立て、カード名・ワザの名前で画面を分けません。

| 段（送る順） | 内容 | 画面 |
|---|---|---|
| 1. ワザ（`role: attack`・1 個） | バトル場のポケモンが今持つワザ（エンジンの `available_attacks`） | 名前（`name_ja`）・必要なエネルギー（`cost`）・**印刷のダメージの表示**（`damage`）・説明（`text_ja`）・出どころ（`route`・`provider`・`payer`・`grantors`）・処理可能性と理由 |
| 2. 宣言といっしょに選ぶもの（`role: declaration_options`・0 個以上・選んだ順） | `addon`: `stadium_coin`（場のスタジアムのコイン）・`attack_power`（ワザを使うポケモン自身の特殊能力）・`with_power`（自分の場のポケモンの特殊能力。`power` の名前） | 1 段目のワザの `options_by_choice` の組だけ。1 つもなければ入力を求めない |

- **ダメージ**: `damage` は印刷の表示（「20」「30×」「10+」・なし）で、与えるダメージの予測ではありません。弱点・抵抗力・効果を GUI で計算しません。受理のあとのダメージ・HP は観測の値で表示します
- **持ち方**: コピー・変身・許可のワザ（`recall`・`psylink`・`prehistoric`・`puppet`・`mimic`）は、エンジンが返した値をそのまま表示します。画像・カード名からワザを補いません
- **宣言といっしょに選ぶもの**: 0 個で送れます。選んだ順のまま送ります（`with_power` は選んだ順に宣言）。重なり・併用の可否は GUI で決めず、入力の検査（エンジンの確かめ）に任せます。ワザを変えたら 2 段目の選択を捨て、前の check の答えも使いません
- **送る前に check**: ワザは、今の入力・今の取っ手への check が通るまで送信できません（`contract/kyuura-client-api-v1.json` の `check_before_submit_kinds`）。ワザの候補は原則 `may_stop_later`（`preflight_not_evaluated`: エンジンの宣言の前の先読みを候補では評価しない）で、check が通っても宣言の受理・完走の保証ではありません
- **宣言のあとの決定**: ワザの対象・トラッシュするエネルギー・山札から選ぶカード・写すワザ・任意の効果は、宣言の前に聞きません。受理のあとにエンジンが出す決定（`answer_decision`・`take_prize` など）に、既存の決定の入力で答えます。本人の回答待ち（「次: あなた（プレイヤー0）の決定への回答」）と相手の回答待ち（相手の画面は「ほかのプレイヤーの操作待ち」）を分けます。山札の中身は、検索が始まって本人の決定の選べるものとして来たものだけを表示します
- **コイン**: 入力にしません。エンジンが投げます
- **本人のうらのバトル場のポケモン**: 本人が知る本当のカードの印刷のワザ（候補にあるカード ID だけ）を `unverified` で示し、宣言といっしょに選ぶものは出しません（エンジンの U7-4 の扱い）。相手の画面・観戦者の画面には出ません
- **知らない形**: ワザの段の並び・`route`・`addon`・`cost` の値・選べるものの項目が契約の表（`stage_roles`・`attack_routes`・`declaration_addons`・`energy_types`・`attack_option_keys`・`addon_option_keys`）にないときは「不明な応答」として操作を止めます

### 拒否と受理のあとの停止

送信の結果は、エンジンの `outcome` と `result.status` のまま区別して表示します（`web/src/state/outcome.ts`）。

| 応答 | 表示 | 状態・取っ手 |
|---|---|---|
| `refused` | 「送らなかった（ホストの段の拒否）」。U7 の段で止め、エンジンに渡していない | 状態は変わらない。`refetch_required` でなければ取っ手は使える |
| `rejected` | 「拒否（エンジン）」。区分（未裁定など）は「ゲーム上の禁止ではありません」と添える | 状態は変わらない。取っ手はエンジンの応答に従う |
| `accepted`・`in_progress` | 「受理」と次の操作（例: プレイヤー1の番の操作） | 古い候補・入力を捨てて取り直す |
| `accepted`・`awaiting_decision` | 「受理（決定待ち）」と、本人か相手かの区別 | 決定の候補を取り直す |
| `accepted`・`halted` | 「受理（そのあと停止）」。宣言の拒否ではないことと、停止の区分・文 | 候補はなくなる。全員の観測が停止を示す |
| `accepted`・`game_over` | 「受理（対戦が終わりました）」 | 終局 |
| `failed`・接続層の誤り | 「処理できない結果」・利用できない表示 | 操作を止める |

拒否では、相手・観戦者への通知・更新を作りません（エンジンの契約。接続層のテスト `server/tests/test_attacks.py`・`server/tests/test_u7_5.py` で確かめる）。拒否・断りの結果には「送ったあなたにだけ表示しています」と書きます。

## トレーナー・場のスタジアム・場の 3 操作（U7-5a〜d）

エンジン 0.170.0 の 5 種類を、候補 → 入力 → check → submit だけで扱います。入力の画面は段の `role`（`trainer`・`energy`・`disguised`・`discard`・`face_down`）・候補の `stadium`・選べるものの `holder` から組み立て、カード名・画像から送る値やコマンドを作りません。5 種類とも、今の入力・今の取っ手への check が通ってから送れます（check が通っても受理・完走の保証ではありません）。

| 種類 | 画面の名前 | 選ぶもの | 受理のあと |
|---|---|---|---|
| `play_trainer` | 手札のトレーナーを使う | 手札のトレーナーカード 1 枚（`role: trainer`）。どうぐ・手札から出すスタジアム・なにかの化石・ピッピ人形・使うと番が終わるカードも同じ操作 | 対象・枚数・費用・山札の検索・任意の選択・相手が答える決定（錯乱ジム・［ちえくらべ］）は、既存の決定（「決定に答える」）で答える。宣言の前に聞かない |
| `use_stadium` | 場のスタジアムを使う | 選ばせるもののない効果（ラッキースタジアムなど）は入力なし（`choices: []`）。エネルギーを選ばせる効果（ヤマブキシティジム・タマムシシティジム）は、エンジンが示したエネルギーカード 1 枚（`role: energy`）と、ついている本人の場のポケモン（`holder`）を表示 | コイン・効果の決定（セキチクシティジムのポケモン・ラジオとうの見る枚数など）は受理のあとの決定 |
| `remove_disguise` | 「ばける」でのせたカードを外す | 自分の場のポケモン（`role: disguised`） | のせたカードは持ち主のトラッシュ。元の姿の最大HPの確かめでエンジンが受け付けないことがある |
| `discard_from_play` | 化石・人形を場からすてる | 自分の場のなにかの化石・ピッピ人形（`role: discard`） | ついているカードもトラッシュ。バトル場が空けば「バトル場に出すポケモンを選ぶ」（`promote_active`）に続く |
| `reveal_face_down` | うらのカードをおもてにする | 自分の場のうらのカード（`role: face_down`。裏面で、カード ID・名前を補わない） | 残るか・トラッシュするかはエンジンが本当のカードで決める（画面は予告しない）。結果は観測で表示し、バトル場が空けば `promote_active` に続く |

- **トレーナーと場のスタジアムの違い**: 手札からスタジアムを出すのは `play_trainer`、場に出ているスタジアムの効果を使うのは `use_stadium` で、別の操作です。`use_stadium` の候補には場のスタジアム（`stadium`。公開のカードと持ち主 `owner`）があり、画面は「持ち主（出したプレイヤー）」と「使うのは番のプレイヤー」を分けて書きます（相手が出したスタジアムも番のプレイヤーが使えます）。同じ番の 2 回目・回数・使えるかは GUI が数えず、エンジンの候補と check に従います
- **処理可能性**: トレーナーとスタジアムは `supported` になりません（`may_stop_later`）。使うための条件をエンジンが前もって確かめないトレーナーは `unverified`（理由 `use_condition_not_evaluated`）で、送れますが使えるかは送るまで分かりません（0.176.0 からは、山札から引いて試す 6 枚も条件を確かめる。下の「山札から引いて試すトレーナー（PT-5e・v0.176）」）。未登録・未裁定（本人のうらのカードをすてる FD1 など）は送れず、「ゲーム上の禁止ではありません」と表示します
- **錯乱ジム（相手が答える決定）**: 使った側の宣言が受理されると、結果に「次: プレイヤー1の決定への回答（相手が答えます。答えるまで待ちます）」と出て、使った側の候補は「ほかのプレイヤーの操作待ち」になります。入力は答える人の画面にだけ出ます（`accept_request`。選べるものを選ぶと「使う」、「選ばない」で辞退）。使えない「使う」はエンジンが拒否し（`rejected`。例 `NO_POKEMON_CARD_IN_HAND`）、診断は答えた人の画面だけに出ます。使ったプレイヤー・観戦者には通知・更新・件数を加えません。拒否のあとは候補を取り直すので、「決定に答える」を選び直して「選ばない」で送ると決定から抜けられます。GUI は自動で再送しません
- **情報境界**: うらのカードは、選べるもの・盤面とも裏面で示し、カード ID・名前・画像を補いません。持ち主の観測にだけある本人の知識（`real`）は、持ち主の画面に文字だけで示します。閲覧者を切り替えると前の閲覧者の観測は捨てます。おもてにしたあと・ばけるを外したあと・すてたあとの表示は、受理のあとの観測だけから作り、古い Canvas はすぐに隠して描画を取り消し、新しい印刷の画像を描きます（今の HP・ダメージは観測の文字）
- **知らない形**: 段の role の並び・選べるもの・`holder`・候補の `stadium` の項目が契約の表（`stage_roles`・`board_option_keys`・`trainer_option_keys`・`stadium_energy_option_keys`・`holder_keys`・`stadium_keys`）にないとき、U7-5 だけの role がほかの種類の段に来たとき、うらのポケモンにカード ID があるときは「不明な応答」として操作を止めます
- **coverage**: 番の候補は `partial` のままです。未対応の種類は `use_power`（特殊能力）・`check_face_up_deck`（おもての山札のカードの確かめ）の 2 つ。種類の外に残る経路（カツラの 2 枚目の「炎」エネルギー・自分のうらのバトル場のポケモンのワザといっしょに選ぶもの）もエンジンの文書のとおり未対応です

検証用の固定例（`server/kyuura_gui_server/scenarios.py`。`server/tools/build_u7_5_scenarios.py` が導入済みのエンジンの公開の入口だけで作る）から始め、接続層のテスト（`server/tests/test_u7_5.py`）と e2e（`web/e2e/u75.spec.ts`）で同じ操作を確かめました。

| 固定例 | 作り方 | 確かめた経路 |
|---|---|---|
| ラッキースタジアム | new_game（エンジンのテストと同じデッキ・seed） | 手札から出す → 入力なしで使う → 同じ番には候補が出ない |
| ヤマブキシティジム | new_game（GUI の側のデッキ。seed は上限を決めた探索） | エネルギーをつける → 手札から出す → エネルギーと holder を選んで使う → 観測で手札にもどる |
| マチスの秘策 | new_game（同上） | 使う → 受理（本人の決定）→ うらにする → 相手・観戦者にカード情報なし → おもてにする（たねポケモンで残る）→ 観測で公開・新しい画像 |
| ピッピ人形 | new_game（エンジンのテストと同じ） | 手札から出す → ベンチからすてる |
| 錯乱ジム | new_game（エンジンのテストのデッキ 対 たねポケモン 1 枚のデッキ） | 錯乱ジム → 交換おじさん → コイン「うら」→ 相手の決定 → 使えない「使う」は相手にだけ拒否 → 同じ取っ手で辞退（接続層）・選び直して辞退（画面） |

「固定例・new_game」はデッキと seed を固定して new_game を始めるだけで、準備から先は通常の合法な操作の列です（画面には seed・デッキ・列を返しません）。構築盤面（エンジンのテストの直接作った盤面）は使っていません。実エンジンの通常の操作で届いていないもの（模擬の応答の単体テストだけ）: `unverified` のトレーナー、本人のうらのカードをすてる FD1、うらのポケモンについているエネルギー（`holder` の `face_down`）、相手が出したスタジアムを使う場面、［ちえくらべ］、どうぐ・化石・番を終えるトレーナー、エネルギーを選ぶタマムシシティジム・コインのあとの決定のあるスタジアム、おもてにしてトラッシュ・すててバトル場が空く場面の `promote_active`、エンジンの `rejected` のうち錯乱ジム以外（MH1 など）。

## 特殊能力（U7-5e）

エンジン 0.171.0（U7-5e）で加わった特殊能力（`use_power`。既存の `UsePokemonPower`）を、候補 → 入力 → check → submit だけで扱います。

- **候補**: 特殊能力の位置ごとに 1 つの候補で、同じ種類の候補がいくつも並びます。画面は候補の `id`（と取っ手）で選び、種類（`kind`）を候補の識別・React の key に使いません。候補ごとに、エンジンが返した特殊能力の名前（`power.name_ja`）と使うポケモン（`pokemon`）を出し、入力の画面には印刷したカード（「ばける」・写した特殊能力では場のポケモンのカードと違うことがある）と、公開カード定義の印刷の説明（位置と名前が合うときだけ）を出します。処理可能性と理由も今までどおり表示します
- **作らないもの**: 常にはたらく特殊能力・反応やワザといっしょに使う特殊能力（エンジンが候補にしない。既存の決定・ワザの宣言で答える）、自分のうらのカードの特殊能力（エンジンが候補にしない）。特殊能力の名前・カード ID から入力の形を推測しません。宣言のない型（`input_disclosure: unconfirmed`）は「入力非公開」として選べるものを出さず、送れません
- **入力の段（0〜3 段）**: 段の `role` は `source`（元のポケモン）・`energy`（エネルギーカード）・`target`（先のポケモン）で、並びは契約の表（`power_stage_shapes`。エンジンの宣言の表の 8 通りと、段のない形）のどれかです。どの段も 1 つを選び（任意の段はない）、段の順のまま送ります。入力のない特殊能力は `choices: []`
- **依存する段**: 2 段目以降は、直前の段で選んだ番号の `options_by_choice` の組だけを出します（3 段目の番号は、前のすべての段の選び方ごとに別。選べるものの `after` が直前の段の番号、段の `upstream_stages` が前のすべての段）。k 段目を変えたら、それに依存する後のすべての段の選択を捨て、前の check の答えも使いません。全段の組み合わせを GUI で作りません。形（段の番号の並び・直前の段への依存・`upstream_stages`・`after` と組の一致）が合わなければ「不明な応答」として操作を止め、形式の版が 1 のままでも、知らない依存の形を読み飛ばして古い 2 段の扱いで送りません
- **送信**: 今の取っ手・今の入力への check が通ってから送れます（通っても受理・完走の保証ではない。`may_stop_later`・`unverified` も同じ）。コインの結果・効果の決定（回復するポケモン・トラッシュする手札のカードなど）は宣言の前に聞かず、受理のあとの既存の決定で答えます。回数（「自分の番ごとに 1 回」など）は GUI が数えず、エンジンが候補に出さないことで分かります
- **情報境界**: 相手のうらのカードは、エンジンが示した位置（場のポケモンの番号・場所）と `face_down` だけで示し、カード ID・名前・表の画像を補いません（うらのカードを指定する組は `unverified`）。選べるものの場のポケモンには、観測の番号から「自分の」「相手の」を付けます。候補・入力は番の主体にだけ届き、相手・観戦者の画面には出ません。拒否は送った人にだけ表示します。特殊能力のあとの移動・進化・回復・特殊状態は、受理のあとの観測から表示します（古い Canvas はすぐに隠して描画を取り消す）
- **エンジンの説明との違い**: エンジンの文書は「新しい項目を無視するクライアントも、直前の段の番号で引けば正しい組だけを選べる」と書いていますが、この GUI はそれに頼りません。この GUI が確かめた範囲は、上の依存の形（直前の段だけへの依存・1 つを選ぶ段・`after` と組の一致・0〜3 段）と、実エンジンで通した 3 つの経路（下の表）だけです

### 実エンジンで確かめた範囲（U7-5e）

| 固定例 | 作り方 | 確かめた経路 |
|---|---|---|
| ロケット団のヒトカゲ | new_game（エンジンのテストの RC_DECK 同士・seed 1） | 番 1 にベンチ 2 匹とエネルギー → 番 3 に［ほのおをもらう］（2 段: 元 → エネルギー）。上流を混ぜた・逆の順・数の違う入力は断る（他者に更新なし）→ 受理 → 観測でエネルギーが移る → ほかの元にエネルギーが残っていても、同じ番には候補が出ない（番ごとに 1 回） |
| ダークユンゲラー | new_game（GUI の側のデッキ。seed は上限を決めた探索） | 番 3 に進化 →［ぶっしつこうかん］（入力なし）→ 受理（本人の決定）→ 手札のカードを選ぶ → 観測のトラッシュ・手札の枚数 → 同じ番には出ない |
| エナジートランス | 再生（準備・ベンチ・進化・エネルギーを U7 の候補で送った 13 コマンド。GUI の対象外の操作は含まない） | ［エナジートランス］（3 段: 元 → エネルギー → 先）。3 段目の番号は 2 段目の選び方ごとに別、混ぜた入力は断る、2 段目を変えると 3 段目を捨てる → 受理 → 本人・相手・観戦者の観測で移る。回数の制限はない |

## 特殊能力・カツラの 2 枚目・おもての山札（U7-5f・g）

エンジン 0.172.0 の U7-5f・g の公開 API（エンジンの `docs/legal-actions-u7-5fg.md`）に追従しました。新しい操作の処理は加えず、候補 → 入力 → check → submit の形のまま扱います。

- **カツラの 2 枚目（attach_energy の任意の 3 段目 `energy2`）**: カツラの効果がはたらく番だけ、エネルギーをつける操作に 3 段目が加わります（`count` 0〜1・`decline`）。3 段目は `path_stages: [1, 2]` と `options_by_path` で引く段で、画面は今の 1・2 段目の選択の番号を `/` でつないだ鍵（`"o1/o8"`）の一覧だけを出します（鍵がない組は 3 段目を選べず、1 枚だけ）。1 段目か 2 段目を変えたら、3 段目の選択と検査の結果を捨てます。送る順は段の順（`[エネルギー, つける先]` か `[エネルギー, つける先, 2 枚目]`）。カツラの許可・炎の判定・つける先・回数・レインボーは GUI で判定せず、エンジンが組と送信で決めます。`options_by_path` の知らない鍵・存在しない参照・重なり・逆の並び・循環（`path_stages` が自分やあとの段を指す）・`options_by_choice`・`depends_on_stage`・`upstream_stages` との併用は「不明な応答」として止めます（U7-5e の依存する段とは別の形として確かめる）
- **おもての山札の確かめ（`check_face_up_deck`。表示だけ）**: 番のプレイヤーの MAIN に、相手の山札の 2 枚目より下のおもての位置が出ます。画面は「表示だけ（送れません）」とし、エンジンが返した `owner`・`position` だけを「相手の山札・上から n 枚目（`position` は 0 がいちばん上）」として表示します。カード ID・uid・名前・表面の画像は補いません。未裁定（FU2）で、ゲーム上の禁止ではありません。`gui_operable_kinds` に加えず、この候補には check・submit を呼びません（inputs だけ）。相手の山札の位置を GUI で列挙しません
- **本人のうらのカードの特殊能力**: マチスの秘策でうらにしたカードの、本人が知る本当のカードの特殊能力が、本人の候補にだけ出ます（`pokemon.face_down`・`power.face_down`。`pokemon` にカード ID はない）。画面は盤面の情報（裏向きのポケモン・場所。盤面の画像は裏面のまま）と、本人が知る本当のカード（`power.card_id`。印刷の情報）を分けて文字で示します。`unverified` を使える・受理されるという意味にしません。入力は 0.172.0〜0.174.0 では 0 段（`choices: []`）か 1 段だけでした。0.175.0 から宣言が 2〜3 段の型も入力を返します（下の「本人のうらのカードの 2〜3 段の特殊能力（U-R3a）」）。完成する組がない場面・宣言のない型などは入力を返さず（入力非公開）、送れません（coverage の R-3）。送ると、エンジンがおもてにしてから受理・拒否・トラッシュを決め、結果は受理のあとの観測で表示します。相手・観戦者の画面には能力の名前・本当のカード・候補・入力は出ません（サーバが出さない。拒否は送った人にだけ表示）
- **coverage の残り（residual）**: `display_only_kinds`・`residual.classes`（R-2〜R-5。API 全体で同じ）・`residual.present`（その応答に当てはまる残り。`public` は公開の状態から、`actor` は本人の候補から）・`partial_residual`・`completeness_basis`・`unverified_paths` を契約の表・型・実行時検証で確かめ、表示で分けます: 評価した種類 ／ 表示だけで送れない種類 ／ 種類の中に示していない経路（R-2 など）／ この応答に当てはまる残り ／ 入力を返していない候補 ／ 送るまで受理が分からない経路。`not_covered_kinds` が空でも「全部の操作に対応」「必ず完走」と表示しません（番のプレイヤーの MAIN は R-2 が残るので partial）。番でないプレイヤー・決定の回答者でも R-4 で partial になることがあり、候補がなくても「操作がない」と言いません（coverage から操作できる主体を推測しない）。残りは届いた主体の応答の範囲だけで表示します（本人の `actor` の残りは相手・観戦者の画面に出ない）
- **検査の答え**: 入力を変えたら、前の check の答えと、変える前に始めた check の遅れた答えを使いません（元の入力に戻しても使わず、検査し直す。U7-5g の上流の変更と同じ扱い）。閲覧者を切り替えたあとの check・submit の遅れた答えも画面に戻りません
- **カツラの番の送信**: 2 枚目を省く（2 段だけ送る）場合も、2 枚の場合も、今の入力への check が通ってから送れます（GUI の決まり。上の「送る前の check」。エンジンは check なしの submit も受け付ける）。2 枚目を選ぶ・変える・外すのも入力の変更で、検査し直します

## 本人のうらのバトル場のポケモンのにげる（P6・v0.174）

エンジン 0.174.0 の P6（エンジンの `docs/legal-actions-p6-face-down-retreat.md`。R-5 の監査で提案された補完）に追従しました。本人のバトル場のポケモンがうら（マチスの秘策）のとき、v0.173 までは入力を返さなかった（R-5・入力非公開）にげるの候補に、入力が付きます。新しい操作の処理は加えず、候補 → 入力 → check → submit の形のまま扱います。

- **入力契約**: 段 1 は入れ替える控え（本人のベンチ。公開）、段 2 はついているカード（0〜枚数・重なりなし・選んだ順）。段 2 は `total_units`（段）と `units`（選べるもの）を省き、`cost_evaluation: {"status": "not_evaluated", "reason": "face_down_reveal_not_evaluated", "omitted": ["total_units", "units"]}` を持ちます。候補は `unverified`（`face_down_reveal_not_evaluated`）・`input_disclosure: confirmed`
- **実行時の検証**（`web/src/api/validate.ts`）: `cost_evaluation` は項目・値・型が契約の表（`contract/kyuura-client-api-v1.json` の `retreat_cost_evaluation`）と同じものだけを受けます。`retreat` のトラッシュの段だけで使われ、`total_units`・`units` との併存、`cost_evaluation` も `total_units` もない費用の段（費用 0 と見なさない）、一部の選べるものだけの `units`、ほかの種類・段の `cost_evaluation`・`total_units`・`units`、知らない値・項目は「不明な応答」として操作を止めます。おもてのにげる（`total_units` とすべての `units`）の検証は今までどおりです。契約の名前・形式の版（1）が同じでも、古いクライアントがこの形を正しく扱えるとはしていません
- **表示**: エンジンが返した控えとエネルギーカードだけを、枚数の範囲・重なりなし・選んだ順で選びます。費用（必要なエネルギーの個数）とカードごとのエネルギーの個数は「評価していません」と表示し、選んだカードの枚数は表示しますが、足りる・足りないとは書きません。本人の観測の `real`・公開カード定義から費用・タイプ・個数を計算しません。盤面のうらのカードは裏面のままです。ねむり・マヒなどを根拠に、うらの候補を GUI で使えなくしません。結果（受理・拒否・そのあとの決定）は予告せず、送信の応答と観測で表示します
- **送る前の check**: 「今の主体・取っ手・候補・入力への check が通っている場合だけ送信できる」という 1 つの条件（`web/src/state/checkGate.ts`）で、送信のボタンと送信の入口（`useEndpointSession` の submit）の両方を守ります。控え・トラッシュするカードの選択・解除・順序の変更、候補・取っ手の変更、閲覧者の切り替えで前の答えを使わず、元の入力に戻しても変える前に始めた check の遅れた答えは使いません（既存の `checkEpoch`）。P6 の check が確かめるのは、選んだ番号が候補にあるか・数・重なり・段の並びなどの形だけで、費用・受理を保証しません（たとえば足りないエネルギーの入力でも形が合えば通り、送ると拒否になることがある）。check・submit を自動で実行・再送しません
- **送信の結果**（エンジンがおもてにしてから決める）: たねポケモンなら、ふつうに確かめて受理（にげる）か拒否です。拒否は送った本人にだけ診断を表示し、状態はうらのまま戻ります（おもてにしたことも相手・観戦者に公開されない）。たねポケモンでなければ、ついているカードといっしょにトラッシュして受理となり、空いたバトル場は既存の決定（バトル場に出すポケモンを選ぶ）で答えます。受理のあと、おもてにしたカードは全員に公開されます（観測で表示）
- **拒否のあとの取っ手**: エンジンの契約では、拒否で取っ手は失効しません（同じ取っ手の check・submit を受け付ける）。GUI は送信のあと（結果によらず）観測と候補を取り直し、取っ手が同じなら選択を残します（既存の取り直しの方針）。自動では送り直さず、送るのは利用者の操作だけです

## カード画像

カード画像は、**エンジンのカード定義から kyuura-card-renderer で作る、非公式のカード風の画像**です。実際のカードの画像・公式の画像ではなく、画像を外部から取得・収集する機能もありません。

- renderer の制限: イラスト枠は白（エンジンのデータにイラストがない）、エネルギーは仮の表示（エネルギーの枠の素材がない）、ベイビィはたねの枠（ベイビィの枠がない）
- 画像を出す場所: 自分の手札、公開のバトル場・ベンチ、おもてのサイド、トラッシュ（開いたときだけ）、スタジアム・使用中のトレーナー、決定の選択肢のうち本人に `card_id` が公開されたもの
- 裏面: 枚数だけが公開された領域（相手の手札・山札・サイド）と、観測が `face_down` のポケモン（最初の番の前の相手の場・マチスの秘策でうらにしたカードなど）。うらのカードの本当のカードは持ち主の観測にだけあり（`real`）、持ち主の画面には文字だけで示します（場ではうらのままなので表の画像は描かない）。相手・観戦者の観測に来たら「不明な応答」として止めます。手札は枚数分（最大 8 枚＋残りの数）、サイドは位置ごと（おもての位置だけ表面）、山札は 1 枚
- 印刷の画像と今の状態: 画像は印刷の値（印刷の HP・ワザ）で、今の HP・ダメージ・特殊状態・ついているエネルギーは画像の隣に観測の値を文字で出す（「印刷の画像」と「今の状態（観測の値）」）。画像の値を今の状態の代わりに使わない
- 画像の選択: 決定の選択肢の画像を押すと、その選択肢の入力（radio・checkbox）を選ぶだけ。送るのは候補の入力の選択肢の id で、画像・カード名から値やコマンドを決めない
- 文字の表示への切り替え: カード定義を取得できない・表にないカード・renderer が変換できない・Canvas や素材画像・フォントの読み込みや描画に失敗した、のどの場合も、カード名と理由を文字で表示する。操作は続けられる。失敗したカードは自動で描き直さない（ページを読み込み直すと描き直す）
- 読み上げ: 表面の Canvas は「〈名前〉の印刷のカード画像（非公式のカード風の画像）」、裏面は場所と枚数（「プレイヤー1・手札（裏向き 7 枚）」）。カード名・ID・HP などは今までどおり文字でも表示する

### 公開カード定義の取得（接続層の拡張）

`GET /api/card-definitions` は **GUI の接続層の拡張の口**です（エンジンの client_api にある入口ではありません）。接続層が、導入済みの kyuura-engine の同梱データ `kyuura_engine/data/kyuura_cards.json` を `importlib.resources` で読み（ソースの checkout・`.venv/src` には依存しない）、描画に使う項目だけを写して返します。

- 識別: `schema: "kyuura-gui-card-definitions"`・`schema_version: 2`、`source`（`format: "kyuura-engine card extract 1"`・`engine_version`・`sha256_method`・同梱データの内容の `sha256`）。表は [`contract/kyuura-gui-card-definitions-v2.json`](contract/kyuura-gui-card-definitions-v2.json)
- `sha256` の方式（`sha256_method: "kyuura-gui canonical-json 1"`）: 読んだ JSON を、キーの並べ替え・空白なしの区切り・ASCII に直さない UTF-8 で直列化したバイト列の sha256。正規化はこの直列化だけで、値・記録の追加と削除・並びの違いは別の値になります（内容の違いを隠さない）。`schema_version: 1` の `sha256` はバイト列の sha256 で方式の識別がなかったので、1 と 2 の値を同じ意味として比べません（画面は知らない方式・版を受け付けない）。同梱データは、エンジンのリポジトリの中身（コミットの blob）では 0.165.0・0.166.0・0.170.0・0.171.0・0.172.0 でバイト列も同じ（1374 件）。導入物のバイト列は、導入した端末の Git の改行の変換（システムの `core.autocrlf=true` など）で変わることがあり、この端末で 0.170.0・0.171.0 を入れた導入物は CRLF、0.172.0 を入れた導入物は LF でした（同じ blob。改行だけの違い）。`sha256`（canonical-json 1）は読んだ JSON から作るので改行によらず、0.166.0・0.170.0・0.171.0・0.172.0 で同じ値（`b82354d6…`）
- 記録の項目: `id`・`jp_set`・`category`・`name`・`pokemon`（段階・進化元・HP・タイプ・弱点・抵抗力・にげる・ルール文・ポケモンパワー・ワザ）・`trainer`（文）・`energy`（基本／特殊・タイプ・文）・`jp_print`（LV・レアリティ）。出典の記録・メモ・URL などは写さない
- **全体の表**（固定版のエンジンでは 1374 件）を返す。対戦の状態（山札・サイド・手札の配分・デッキリスト）を読まず、対戦で使っているカードだけの表は作らない（対戦の構成が分かってしまうため）。プロセスの中で 1 回だけ作り、使い回す
- 形の合わない記録・同じ ID の重なった記録は表に入れず `omitted` に数える（画面は「カード定義にないカード」）。同梱データを読めなければ `GUI_CARD_DATA_UNAVAILABLE`（503）
- フロントは応答を項目ごとに確かめて renderer の `EngineCardRecord` の形に組み立て直す（`as` で型を決めつけない。`web/src/cards/definitions.ts`）。観測やカード名の表（`/api/cards`）は描画に要る形ではないので使わない
- **表を持っていることと、非公開のカードが何かを知ってよいことは別**です。表面を描くのは、閲覧者の観測にカード ID があるカードだけ。表（キャッシュ）で表示の権限を判定しない

### 非同期の描画と非公開の情報

renderer の世代の管理（同じ Canvas では最後の要求だけが描く）は、**すでに描かれたピクセルを消しません**。GUI は次のようにします（`web/src/cards/CardImages.tsx`）。

1. 描く内容ごとに別の Canvas を作る（カード ID が変わる・表面から裏面になる・閲覧者を切り替えて画面ごと作り直す、のどれでも古い Canvas を使い回さない）
2. 内容の変更・部品の破棄では、effect の cleanup で `cancelRenderToCanvas` で待機中の描画を無効にし（キャンセル）、同時に Canvas をすぐに隠して幅・高さを 0 にしてピクセルを消す（消去）。キャンセルは「古い内容をこれから描かせない」、消去は「今見えている古い内容を消す」役割で、両方を行う
3. 新しい内容は、描けた（`true`）ときだけ表示する。それまでは文字の「画像を準備中」

- キャンセル後の `false` はエラーとして表示しない。cleanup のあとに終わった古い要求の完了・失敗は、その effect の目印で無視する（新しい表示を変えない）。React の StrictMode（effect の 2 回の実行）でも同じ
- 裏面の部品はカード ID・名前を受け取らない（props・DOM の属性・`title`・`aria-label`・画像の名前に入りようがない）。裏面の画像は 1 回だけ描いて全部の裏向きのカードで共有する（カードの情報を含まない静的な画像。裏向きのカードごとに Canvas を作らない）
- 表面の描ける内容の使い回しは、公開カード定義の表のカード ID だけをキーにする（閲覧者・秘密の状態をキーに入れない）。同じカードは同じ内容のオブジェクトなので、親の再描画で描き直さない

## 未対応の操作

この API の版（U7-1〜U7-5g）で、番のプレイヤーの MAIN に評価しない種類はなくなりました（`not_covered_kinds` は空）。ただし、全部の操作に対応した・必ず完走するという意味ではありません。表向きの山札のカードの確かめ（`check_face_up_deck`）は表示だけで送れず（未裁定。ゲーム上の禁止ではない）、エンジンの文書の残り（R-2: 自分のうらのバトル場のポケモンのワザといっしょに選ぶもの、R-3: 自分のうらのカードの特殊能力のうち入力を作れない型、R-4: 番のプレイヤーの MAIN のほかでの表向きの山札のカードの確かめ、R-5: 入力を返さない候補）は作っていません（v0.174 の P6 で、本人のうらのバトル場のポケモンのにげるは入力が付き、この候補は R-5 から外れた。R-5 のほかの候補は残る）。トレーナーでの進化・にげる以外の入れ替えなどエンジンの候補にない操作も作っていません。常にはたらく特殊能力・反応やワザといっしょに使う特殊能力は、新しい操作として作らず、既存の決定・ワザの宣言で答えます。画面では coverage の表示だけの種類・示さない経路・当てはまる残り・入力を返さない候補・未確認の経路を分けて表示します（「特殊能力・カツラの 2 枚目・おもての山札（U7-5f・g）」の章）。ダミーの対戦処理はありません。

ワザ・トレーナー・場のスタジアム・特殊能力で終局・停止まで進められますが、上の残りがあり、通常の対戦機能の完成・必ず完走するという意味ではありません。

決定待ち（サイドを取る・宣言のあとの決定）は、U7-4 から通常の new_game の画面操作でも届きます（e2e `attacks.spec.ts`・`u75.spec.ts`）。サドン・デスなど通常の操作で届かない場面のために、**検証用の固定例**も残しています（エンジンのテストの既存の固定例。ピカチュウのデッキ・seed 9 で受理された操作の列を接続層が公開の `new_game`・`apply_command` で再生し、`ClientHub.from_state` で包む。再生は API の外のホストの側の準備で、ブラウザへ seed・デッキリスト・操作の列は返しません）。停止の固定例は、たねポケモン 1 枚のデッキ同士（seed 1）で準備の補償が記録で決まらず停止する例です。この 3 つは記録したエンジン（`ffcc5ca`）の来歴を書き換えず、新しい版で確かめた結果を `compatibility` に追記しています（0.165.0・0.166.0・0.170.0・0.171.0・0.172.0・0.174.0。違いは候補の `implemented_kinds` に種類が加わったことと、0.172.0 で coverage に項目が加わったことだけで、どの時点にも U7-4・U7-5 の候補は出ない）。U7-5 の 6 つの固定例（記録したエンジンは `0885d66`。0.171.0・0.172.0 で確かめた結果を同じく追記した）・U7-5e の 3 つの固定例（`74c8e1f`。0.172.0 の結果を追記した）・U7-5f・g の 3 つの固定例（`e26df79`）は、それぞれの章のとおりです。0.174.0 では 14 の固定例すべてで、0.172.0 と全入口の view・candidates・作成の知らせが同じでした（`compatibility` に追記。記録は作り直していない）。

## 接続層の責任と HTTP の口

接続層（`server/kyuura_gui_server`）は ClientHub を包む薄い層です。

- ClientHub の作成と保持。初版は単一の対戦だけを持ち、新しい対戦を作ると古い対戦（hub・入口・更新）を捨てる
- プレイヤー0・1・観戦者・ホストの入口を Python 側で保持し、ブラウザにはローカル用の関連付けの識別子だけを渡す。ホストは別の口
- 要求に actor・viewer を書いて主体を選ぶ口はない（書けばエンジンが `CLIENT_FIELD_UNKNOWN`）
- 要求（client_api の JSON）を入口の `handle` へそのまま渡し、応答を送り手へそのまま返す
- 閲覧者ごとの公開の更新を、要求のたびに hub から取り出して上限つき（閲覧者ごと 100 件）で保持する。保持の範囲より古い位置は `gap` で、view の取り直しへ誘導する
- 同じ対戦への要求を対戦ごとの鍵で 1 つずつ処理する
- 誤りは決まった文（`GUI_*`）。例外の文・traceback を返さない。ブラウザ向けの応答に、エンジンの閲覧用記録の禁止項目（seed・乱数・確認値・コマンド・デッキリストなど）が入っていないことを最後に確かめる
- seed は接続層が `secrets` で決め、返さない・受け取らない。テスト専用の起動の設定 `--test-fixed-seed N`（e2e が使う）だけが固定する（seed はブラウザへ返らない。`npm run dev` では使わない）
- ClientHub の内部状態には触れない（使うのは `start`・`from_state`・`player`・`spectator`・`host`・入口の `handle` だけ）
- 固定例（再生）と構築盤面（テスト専用）は `ClientHub.from_state` で包む。0.177.0 から、不変条件の崩れた状態をエンジンが hub を作る前に拒否する（`UnusableStateError`）。接続層は既存の `GUI_INTERNAL_ERROR`（決まった文）だけを返し、問題の文（`problems`）・原因（`__cause__`）・traceback・例外の型をブラウザへ返さない（ホストのログだけ）。拒否では対戦を作らず、前の対戦はそのまま残る（「構築した状態の入口の確かめ」）

| 口 | 内容 |
|---|---|
| `GET /api/health` | 接続層・エンジンの版、契約の識別 |
| `GET /api/decks/presets` | エンジンの固定デッキ（サンプル）と規約集合 |
| `GET /api/cards` | カード名の表（ID・日本語名・分類・段階・HP） |
| `GET /api/card-definitions` | 描画用の公開カード定義の全体の表（GUI 接続層の拡張。「カード画像」） |
| `GET /api/scenarios` | 検証用の固定例の一覧 |
| `POST /api/local-match` | 対戦の作成（`{"mode":"decks","decks":[{"entries":[{"card_id","count"}]},…],"conventions"?}` か `{"mode":"scenario","scenario"}`）。古い対戦を捨てる |
| `DELETE /api/local-match` | 対戦を捨てる |
| `POST /api/seat/{token}` | プレイヤー・観戦者の入口へ client_api の要求（view・candidates・inputs・check・submit） |

## 主体・秘密の情報・拒否・取っ手の扱い

- 閲覧者の画面は (対戦, 入口) ごとに作り直すので、切り替えると前の閲覧者の手札・候補・診断・ログはフロントエンドの状態から消える。主体の違う応答をキャッシュで混ぜない
- 切り替え前・取り直し前の応答が遅れて届いても、世代の番号で捨てる
- 拒否（エンジンの拒否・ホストの段の拒否・要求の誤り）は送り手の画面だけに表示し、他の閲覧者の更新は作られない（エンジンの契約。接続層のテストで確かめる）
- 受理のあとは古い候補・入力を捨てて取り直す。`refetch_required` の拒否でも取り直す
- `operation_id` は対応付け用（重複の排除はない）。submit は自動で再送しない。結果の分からない通信失敗は「送信の結果が分かりません」と表示し、今の観測を取り直す
- 二重クリック・並行送信は、画面の送信の門（閲覧者とホストで共有）と接続層の鍵で防ぐ
- 更新の番号はエンジンの `number`（受理でだけ進む）。状態のハッシュは使わない。再取得は現在の view を基準にし、接続前の秘密の情報を履歴として作らない
- 処理可能性（`supported`・`may_stop_later`・`unresolved_ruling`・`not_implemented`・`technical_limit`・`unverified`）と入力の公開区分（`input_disclosure`）を分けて表示する。未裁定・未実装を「ルール上禁止」とは表示しない。`supported` でも guarantees の範囲を超えて完走を保証しない。coverage の `complete` は「明示した種類の候補がそろう」意味で、全合法手の完成ではない

## 制限

- 単一の対戦だけ。永続化・オンラインの再接続・認証・通信の暗号化・重複の排除はない
- エンジンの対戦ログ（`visible_log`）は client_api 形式 1 の応答に含まれないため、ログ欄は閲覧者に届いた公開の更新の要約（段階・番・入力待ち・公開の枚数・停止・結果）で、完全な対戦ログではない（ワザ・トレーナー・スタジアム・特殊能力のコインの結果・ダメージの計算の経過・おもてにしたカードの判定の経過などは載らない。受理のあとの状態は観測で表示する）
- カード画像は非公式のカード風の画像（イラスト枠は白・エネルギーは仮の表示・ベイビィはたねの枠）。実際のカードの画像ではない。描けないときは文字の表示。カード名はエンジンの同梱のカードデータの表
- 本番ビルドは Web フォント（Noto Sans JP の文字の範囲ごとのファイル）と素材画像を含むため大きい（約 21 MB・548 ファイル。フォントは使う文字の範囲だけを読み込む）
- デッキの検査はエンジンの `deck_problems` の結果をそのまま表示する。広いデッキビルダーはない
- パッケージの公開・外部公開・デプロイはしない
